# Sharing Configuration Across Gradle Subprojects Using Convention Plugins

As your Gradle project grows and you add more subprojects, you'll likely find yourself copying and pasting similar configuration blocks across multiple `build.gradle.kts` files. This repetition not only violates the DRY principle but also makes your build configuration harder to maintain. Convention plugins offer a clean solution to this problem by allowing you to centralize and share common configuration.

## What are Convention Plugins?

Convention plugins are project-local plugins that live in your build logic and help you encapsulate and reuse common configuration across subprojects. They're different from binary plugins (like the Java plugin) in that they're specific to your project and live alongside your build files.

## Setting Up Convention Plugins

First, create a `buildSrc` directory in your project root. This special directory is where we'll put our build logic:

```kotlin
// Project structure
.
├── buildSrc
│   ├── build.gradle.kts
│   └── src/main/kotlin/
├── settings.gradle.kts
└── subprojects/
    ├── app
    └── library
```

In your `buildSrc/build.gradle.kts`, add:

```kotlin
plugins {
    `kotlin-dsl`
}

repositories {
    mavenCentral()
}
```

## Creating Your First Convention Plugin

Let's create a convention plugin for Java library configuration. Create a new file `buildSrc/src/main/kotlin/com.example.java-library.gradle.kts`:

```kotlin
plugins {
    `java-library`
    id("com.example.java-common")
}

java {
    toolchain {
        languageVersion.set(JavaLanguageVersion.of(17))
    }
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:5.9.2")
}

tasks.test {
    useJUnitPlatform()
}
```

And a common base plugin `buildSrc/src/main/kotlin/com.example.java-common.gradle.kts`:

```kotlin
plugins {
    java
}

repositories {
    mavenCentral()
}

tasks.withType<JavaCompile>().configureEach {
    options.encoding = "UTF-8"
    options.compilerArgs.add("-Xlint:unchecked")
}
```

## Using Convention Plugins

Now you can apply these plugins in your subprojects with minimal configuration:

```kotlin
// subprojects/library/build.gradle.kts
plugins {
    id("com.example.java-library")
}

// That's it! All the common configuration is inherited
```

## Benefits of Convention Plugins

1. **Centralized Configuration**: Changes to common settings can be made in one place
2. **Type-Safe Configuration**: Using Kotlin DSL provides IDE support and compile-time checking
3. **Easier Maintenance**: No more copy-pasted configuration blocks
4. **Better Organization**: Build logic is separated from build files

## Advanced Usage: Extending Convention Plugins

You can make your plugins more flexible by adding extension properties:

```kotlin
// buildSrc/src/main/kotlin/com.example.java-common.gradle.kts
interface JavaCommonExtension {
    var javaVersion: Int
}

val Project.javaCommon: JavaCommonExtension
    get() = extensions.getByType()

extensions.create<JavaCommonExtension>("javaCommon")
```

This allows subprojects to customize specific aspects while inheriting the rest:

```kotlin
// subprojects/app/build.gradle.kts
plugins {
    id("com.example.java-library")
}

javaCommon {
    javaVersion = 11 // Override just this setting
}
```

## Best Practices

1. Keep plugins focused and single-purpose
2. Use meaningful names that reflect their functionality
3. Document your plugins with KDoc comments
4. Consider creating a README in your `buildSrc` directory
5. Use version catalogs for dependency management

## Conclusion

Convention plugins are a powerful tool for managing build configuration in multi-project Gradle builds. They help maintain consistency across subprojects while keeping your build files clean and maintainable. As your project grows, investing time in well-structured convention plugins will pay dividends in reduced maintenance overhead and improved build configuration clarity.

Remember to start simple and gradually extract common configuration as patterns emerge in your build scripts. Not everything needs to be a convention plugin, but when you find yourself copying the same configuration across multiple subprojects, it's a good sign that you might benefit from one.
